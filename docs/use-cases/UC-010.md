# UC-010 - El agente planifica y ejecuta una tarea de análisis multi-paso

| Campo | Valor |
|-------|-------|
| **ID** | UC-010 |
| **Título** | El agente planifica y ejecuta una tarea de análisis multi-paso |
| **Prioridad** | P1 |
| **Estado** | Aprobado |
| **Versión** | 1.0 |
| **Fecha** | 2026-08-13 |

## Actores

- **Usuario**: profesional de QA que plantea una solicitud cuyo cumplimiento
  requiere más de una observación del proyecto (por ejemplo, priorizar qué
  clases conviene probar).

## Descripción

El usuario plantea una solicitud que el agente no puede satisfacer con una sola
herramienta. El agente **percibe** la intención (qué pide y sobre qué objeto
real), **piensa** un plan multi-paso con criterio de éxito, **actúa** ejecutando
pasos con herramienta y parámetros decididos por razonamiento, **observa** los
resultados reales, **reflexiona** si la evidencia satisface la intención y
**decide** iterar o concluir. Todo el razonamiento queda visible para el usuario
antes de la respuesta final. Este caso de uso materializa la transición de
chatbot a agente (ver `specs/001-core-ai-qa-agent/agent-reasoning-loop.md`).

## Disparador

El usuario envía una solicitud cuya satisfacción requiere varios pasos de
herramientas, o cuyo objetivo no se deduce de una única observación.

## Precondiciones

1. El usuario tiene acceso explícito y autorizado al proyecto (allowlist).
2. El backend LLM soporta las operaciones de razonamiento (`planificar`,
   `razonar`, `evaluar`, `responder`).
3. Al menos una herramienta del catálogo es pertinente al objetivo.

## Flujo Principal

1. El usuario envía una solicitud que requiere análisis multi-paso (por ejemplo,
   "¿cuáles clases son las más importantes de probar?").
2. El agente percibe la intención: objetivo (priorizar pruebas) y entidad
   (clases del proyecto).
3. El agente genera un plan explícito con criterio de éxito (por ejemplo:
   explorar estructura → localizar clases → buscar definiciones → priorizar).
4. El agente presenta el plan y el razonamiento de cada paso al usuario.
5. Para cada paso pendiente:
   a. El agente elige herramienta y parámetros, validados contra el esquema y
      la allowlist.
   b. Si la acción es sensible, solicita autorización (SC-004); si se deniega,
      re-planifica con un paso alternativo no sensible (FR-036).
   c. Ejecuta la herramienta y registra la observación real en el historial
      visible con su razón.
   d. Reflexiona: evalúa si la evidencia acumulada satisface la intención.
6. Si el criterio de éxito se cumple, concluye; si no, itera (hasta `pasos_max`).
7. El agente produce la respuesta final anclada en las observaciones reales,
   con confianza acorde y recomendaciones etiquetadas si corresponde.
8. El caso de uso termina.

## Flujo de Excepción 5b - Autorización denegada

1. Un paso sensible es denegado por el usuario.
2. El agente elige un paso alternativo no sensible si existe.
3. Si no existe alternativa, responde con la evidencia acumulada y confianza
   `limitada`/`sin_informacion`.
4. El caso de uso termina.

## Flujo de Excepción 5d - Sin más evidencia obtenible

1. El agente evalúa que ninguna herramienta restante aportaría evidencia nueva.
2. El agente concluye con la evidencia acumulada.
3. Si la intención no quedó satisfecha, lo comunica y ofrece recomendaciones
   etiquetadas (no como hechos).
4. El caso de uso termina.

## Flujo de Excepción 6 - Límite de pasos alcanzado

1. El agente alcanza `pasos_max` sin satisfacer el criterio de éxito.
2. El agente responde con la evidencia obtenida y confianza
   `limitada`/`sin_informacion` (SC-016), sin inventar lo que no observó.
3. El caso de uso termina.

## Postcondiciones

1. El usuario ve el razonamiento por pasos (razón + herramienta + parámetros +
   observación) antes de la respuesta final (FR-035 / SC-015).
2. La respuesta final se basa exclusivamente en observaciones reales (SC-017).
3. Ninguna acción sensible se ejecutó sin autorización (SC-004).
4. El historial visible registra cada paso y su resultado real (FR-020).

## Ejemplo (priorización de clases a probar)

- **Solicitud**: "¿cuáles clases son las más importantes de probar?"
- **Percepción**: objetivo = priorizar pruebas; entidad = clases del proyecto.
- **Plan**:
  1. `explore` (razón: conocer la estructura y capas) → observación: BLL, DAL, UIL.
  2. `search` con regex `class\s+\w+` (razón: obtener las definiciones reales de
     clase) → observación: lista de clases por capa.
  3. `search` por marcadores de prueba (razón: saber qué está ya cubierto).
  4. `evaluar`: la evidencia es suficiente → concluir.
- **Respuesta**: priorización anclada en las clases reales observadas; si la
  evidencia es insuficiente, confianza `limitada` + recomendaciones.

### Ejecución real (2026-08-13, proyecto ReservaHotel, backend NVIDIA NIM)

Solicitud: *"¿cuáles clases son las más importantes de probar?"*. El agente
percibió la intención, generó un **plan multi-paso de 3 pasos** y respondió
priorizando las clases reales observadas:

- **Razonamiento (visible)**:
  `1. Explorar la estructura general del proyecto para localizar directorios de
  código fuente y archivos de pruebas → explore {'ruta': '...\ReservaHotel', 'profundidad_max': 4}`
  `2. Buscar todas las definiciones de clases en el código fuente → search {'patron_regex': 'class\s+(\w+)', ...}`
  `3. Localizar las definiciones de clase con metadatos estructurados → locate {'patron': 'class', 'tipo': 'clase'}`
- **Respuesta (confianza `limitada`)**: priorizó las clases reales de BLL
  (ClienteBL, PagoBL, ReservacionBL, UsuarioBL, ...) y DAL (ClienteDAL, ...),
  y fue honesta: sin evidencia de criticalidad/complejidad no afirmó un ranking
  que no podía sustentar (SC-017).
- **Recomendaciones (etiquetadas)**: revisar reglas de negocio/casos de uso,
  evaluar complejidad de métodos BLL y revisar defectos históricos para
  priorizar por riesgo.

Notas de la ejecución real:
- La ruta autorizada se **inyecta** cuando el LLM propone un parámetro distinto
  (`ruta_base`) o rutas con doble escape JSON en Windows (FR-025).
- `planificar()` usa el catálogo con **esquemas de entrada** y **deduplica**
  pasos idénticos; `evaluar()` es estricto (la estructura sola no satisface una
  petición de clases) y `responder()` recibe la intención para atenderla
  directamente.

## Notas

Este caso de uso no reemplaza las garantías de honestidad: el razonamiento es
hipótesis, pero la respuesta final solo afirma lo anclado en observaciones
reales (UC-007). El router determinista se mantiene como primera pasada para
solicitudes simples de una sola herramienta.
